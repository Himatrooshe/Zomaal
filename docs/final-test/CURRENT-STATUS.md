## API gaps and external prerequisites

- **Missing/undefined API features:** overdue customer/COD payment alerts, Sendit sync-failure alerts, Shop invoice download, dedicated reorder, Shop courier-name response, and platform-request submission. Do not present these as complete. Confirm design/client requirements before implementation; reorder can be assembled manually but has no atomic replay contract.
- **Payments:** Moroccan gateway/web checkout and stored cards are unimplemented. Manual admin activation exists; the last live plan read returned an empty active-plan list. Admin plan setup is still needed. No gateway payment/refund acceptance is claimed.
- **Provider/configuration:** Ameex firewall allowlisting; Sendit connection; Meta app/access/template/sender setup for WhatsApp; provider permissions/client-side Meta fix for Ads; FCM deployment and a real device for push. These are distinct from missing API routes.
- **Product/client scope:** detailed Item Value design, full notification trigger list, risk/cancellation/staff-limit policies and ad-product allocation need the documented client decisions. Reports, TikTok and Snapchat are excluded from this QA pass. Existing TikTok code is not a QA completion claim.
- **Unverified acceptance:** real courier Delivered/Returned callbacks and financial results, controlled parcel matching, physical labels/device scans, actual WhatsApp/push receipt, full plan lifecycle and the specifically untested onboarding paths.
- **Verification limit:** historical reports record passing scoped lint, build and automated gates, but also pre-existing repository-wide lint failures. Do not claim the full repository is lint-clean or that all 405 operations were live-tested.

## How to use the handoff

Frontend: read your module frontend guide and production schema, then handle loading/empty/validation/permission/plan/disconnected/incomplete-value states. QA: read the module QA guide and latest verification first; repeat unchecked acceptance on disposable data. Preserve the retained account and original data. Never place real charges, messages or courier shipments merely to simulate a passing scenario. Original JSON observations are retained unchanged; old failures are historical and are not rewritten into passes.

Shop/customers alternate folders link to their detailed handoffs. All modules and the shared tracking workflow are listed in the root README. Documentation refresh dates are separate from execution dates.
